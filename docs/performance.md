# 性能排查与验证

## 先区分开销在哪里

| 排查优先级 | CPU / 内存 / GPU 开销来源 | 本项目的处理 | 证据边界 |
| --- | --- | --- | --- |
| 1 | 视频解码、视频帧缓存、分辨率缩放 | 默认720p24；关闭视频音轨；另提供原生纯视频方式 | 视频确实占用解码和帧缓存，但没有在宿主中逐项测出它占总资源的百分比 |
| 2 | 全屏视频与透明层的桌面合成、宿主浏览器进程 | 关闭额外全屏模糊/滤镜；小画布；其他应用前台时由宿主暂停 | GPU占用必须看对应机器的Video Decode、3D和进程数据；JS计时不覆盖这些工作 |
| 3 | 雪花Canvas清屏、图形命令和静态频谱的无效计算 | 24片雪花三批fill；静态频谱跳过64频段循环；12fps | 页面采样和绘制次数可以验证，但不等于全系统CPU/功耗 |
| 4 | 关闭特效后仍分配的Canvas及重复运行代码 | 无用画布1×1、按需申请context；四套源码合为一套 | 可以确认逻辑画布大小和源码重复减少，不能据此推算整个宿主RSS |
| 5 | 日期/时钟和参数更新 | 默认每分钟更新；不显示秒数；参数修改不反复重建粒子 | 开销较小，优先级低于视频与绘制 |

这是基于代码、资源尺寸和页面采样的排查顺序，**不是已经实测完成的宿主CPU/GPU百分比排名**。没有为了采样修改屏幕分辨率、驱动或其他应用。

## 本次可量化的页面前后对照

基线为提交 `75f2ae8` 的snow-v2；优化后为共享核心版本。Windows上的Google Chrome无头浏览器，1920×1080视口、DPR=2、同一720p24 VP9视频；每场景采3次，每次约3秒，下表取中位数。音乐数据由测试脚本合成。

CDP的 `ScriptDuration` 是页面脚本累计耗时；`TaskDuration` 是渲染主线程任务累计耗时。表中的毫秒数是**整个3秒采样窗口的累计量**，不是每一帧的耗时，也不是进程CPU百分比。

| 场景 | 脚本耗时：前 → 后 / ms | 页面任务耗时：前 → 后 / ms | 绘制次数：前 → 后 |
| --- | --- | --- | --- |
| 网页视频，关闭叠加层 | 0.000 → 0.000 | 3.738 → 3.115 | 0 → 0 |
| 24片雪花，静音 | 3.118 → 2.553 | 13.381 → 10.966 | 35 → 33 |
| 24片雪花，模拟音乐 | 8.347 → 8.421 | 20.409 → 18.897 | 36 → 32 |
| 宿主暂停 | 0.000 → 0.000 | 2.439 → 2.655 | 0 → 0 |

静音雪花场景的脚本累计耗时有所降低，但采样中的实际帧数也不同。模拟音乐场景的脚本耗时没有稳定降低，不能声称所有场景CPU都下降。三秒窗口较短且受调度、测试驱动和浏览器影响，这些数值只用于页面回归检查。

暂停场景页面新增绘制次数为0，采样脚本耗时为0；浏览器/音频服务/宿主本身仍可能有开销，不能说整个程序绝对0 CPU。

`video-only`仍是关闭网页叠加层后的video元素，不是Wallpaper Engine/Muro的原生纯视频运行实测。

## 内存：可以确认与不能确认的部分

- 旧版即使关闭雪花与频谱，也保留640×360和640×320两张画布，共435,200个逻辑像素。新版关闭后为两张1×1，共2个像素。按RGBA一个缓冲区估算，避免约1.66MiB的逻辑像素存储；浏览器物理分配、GPU副本和回收时机另计。
- 省电版保留频谱、关闭额外雪花时，频谱640×320保持不变，雪花画布由640×360缩为1×1，避免约0.88MiB的逻辑RGBA存储。
- 雪花版同时打开两个图层时仍需同样大小的画布，不声称活动雪花画布的内存下降。
- 采样JS堆约1–2MiB，且没有强制GC；它不包含视频解码缓存、GPU显存、浏览器原生对象、宿主进程和系统合成器，不能当作整款壁纸的内存占用。
- 原生视频解码器有多张帧缓冲，具体数量依赖硬件和实现。不能从文件大小推导运行内存，更不能把工作集求和直接当作独占物理内存。

## GPU与分辨率

1080p约29.97fps的视频每秒约62.1百万像素，720p24约22.1百万像素；后者的源视频像素速率约少64%。这只是分辨率×帧率的数学比较，**不是GPU利用率下降64%**。单张YUV420视频帧在720p约1.32MiB、1080p约2.97MiB，实际解码器会另有缓存和表面。

原生纯视频方式可省去本项目的网页叠加层，但宿主也会使用自己的视频播放与合成流程，实际收益需在对应机器比较。

真实GPU改善目前没有可靠的前后测量；Mac/Muro没有真实硬件实测。Windows WebKit只用来验证事件与暂停行为，其媒体尺寸报告不用于证明Mac解码性能。

`preload="metadata"`只是预加载提示，自动播放时浏览器仍可能缓冲更多内容；它不是强制内存上限，也不据此宣称内存节省。

## 具体清理

- 四份核心JS/HTML/CSS合为 `src/` 一份，版本只覆盖配置，平台只保留宿主适配。
- 音频缓冲复用；暂停或关闭频谱时在Windows适配层直接返回。宿主仍可能保留自己的音频监听服务，页面不能保证注销宿主监听。
- 频谱平滑的指数计算由每次64次改为2次；静态时整段跳过。
- 雪花每帧fill由24次改为3次；没有邻居连线、逐粒子模糊、投影和鼠标追踪。
- 去掉重复的音频过期判断，使用单个看门狗；暂停时取消绘制、时钟和音频定时器。
- 独立打包Windows/Mac、两个互动版本和纯视频，eco包不再带1080p文件。磁盘空间减少与运行内存减少是不同指标。

## 复现与宿主测量

```sh
python tools/profile.py --root dist/windows/snow-v2 --out performance.json
python tests/smoke.py --root dist
python -m unittest discover -s tests -p test_build.py
```

`tools/profile.py`只读页面指标。不要把不同浏览器、视频、分辨率、前后台状态的结果直接相减。

在真实宿主中，应分别对比省电互动版、雪花互动版和原生纯视频，使用同一屏幕、同一前台桌面状态、同一系统音频、相同采样时长；分开记录进程CPU、私有内存/工作集、GPU 3D、Video Decode和显存。桌面被遮挡导致暂停时的0%样本不能代表播放负载。

原始页面采样在 `docs/measurements/page-before-after.json`。接口依据：[CDP Performance](https://chromedevtools.github.io/devtools-protocol/tot/Performance/)、[Canvas优化建议](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)、[preload含义](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/preload)。
